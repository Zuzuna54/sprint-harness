# Architect Review — harness-audit-resolution-and-scope-v1

> **Reviewer:** principal architect (sprint design lock gate)
> **Spec:** [`spec.md`](./spec.md) (assembled 2026-05-19T17:45:50Z, wizard sections A/H/I/J)
> **Plan source-of-truth:** `~/.claude/plans/hazy-gathering-kettle.md`
> **Verdict:** **APPROVED with 3 conditions** (see [§ Conditions for Approval](#conditions-for-approval))
> **Scope:** 19 ACs across 4 waves — scope-bounding (W1) + audit-resolution phase (W2) + HAR-1..10 fixes (W3) + docs/polish (W4)

This sprint converts two load-bearing failure modes (100% noise repo-wide audit + audit-to-bypass-to-ship pattern) into deterministic in-scope signal + a phase with real fix capacity. Both gaps were proven empirically by the immediately-prior sprint (`harness-truthful-docs-and-wiring-v1`, closed 2026-05-19) where 10/10 audit findings landed out of scope and were deferred via gate_bypasses. The fix lands BEFORE v0.8.0 legacy-bypass removal — correct sequencing; bypass removal without the resolution phase would simply harden the ship-with-known-vulns pattern.

The architecture below is sound. Five formal ADRs capture the load-bearing decisions; three conditions must hold by sprint-end for the harness to remain truthful.

---

## 1. AC-1+2+3+4 — Scope-bounded audit gate (post-filter at gate, not at worker)

### Architectural choice

Mirror the existing `gate_testgaps_blocks` pattern in `scripts/lib/worker-gates.sh:58-106` exactly:

1. Worker (`ruflo daemon trigger audit`) continues to scan the whole repo — the daemon prompt-internals are untouched.
2. `gate_audit_blocks` accepts `<audit-json>` + `<slug>`, parses `spec.md ## Files touched` (same awk/grep tokenizer used by gate_testgaps:78-80), then partitions `.vulnerabilities[]` by `.file in files_touched`.
3. **In-scope vulnerabilities** count toward the blocking gate (zero-tolerance, preserves Q2 semantics).
4. **Out-of-scope vulnerabilities** are logged as advisory and counted into a separate state field.

This is the right call because:

- **No new failure modes.** The testgaps pattern is already battle-tested across 11 sprints. Reusing the awk parser, the vacuous-pass behavior (empty `## Files touched` -> PASS), and the post-filter timing means we inherit the same correctness guarantees.
- **Worker remains stateless.** The daemon does not need to know about sprint slug, files_touched, or any sprint-specific state. The slug-aware logic stays in bash where state lookup is one `jq` call.
- **Rollback is one line.** If post-filter misbehaves, revert worker-gates.sh and audit is back to repo-wide. No daemon redeploy.

### Concern — out-of-scope findings must not be silently buried

Post-filter is correct, but it creates a new risk: **legacy noise accumulates invisibly**. If sprint N has 10 out-of-scope findings and sprint N+1 has 10 out-of-scope findings (likely the same 10), nothing forces anyone to ever look at them. The audit-bypass pattern simply moves up a layer — from bypass-at-gate to ignore-in-advisory-log.

### Recommendation — visibility in retro

`dashboard.html` (generated by retro phase) MUST surface an **in-scope vs out-of-scope vulnerability ratio per audit run**. State shape addition:

\`\`\`json
"audit_runs": [{
"ran_at": "...",
"vulnerabilities_in_scope": 0,
"vulnerabilities_out_of_scope": 10,
"out_of_scope_har_ids": ["legacy-HAR-1", "legacy-HAR-2", "..."]
}]
\`\`\`

The dashboard renders this as a stacked-bar visualization in the retro view. When the out-of-scope count grows over time without a remediation sprint, this becomes self-evidently a technical-debt signal — not a hidden one. **This is ADR-1.**

## 2. AC-5 — `audit-resolution` phase (12th phase, between `verifying` + `pre-deploy`)

### What changes

Adding a phase is a **7-file ripple** per the existing recipe (validated by `harness-deterministic-phases-v1`):

| #   | File                                        | Change                                                                                                                                                                                                                                                                                               |
| --- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `scripts/lib/phase-manifest.json`           | New `audit-resolution` block: advances_to=[pre-deploy, paused], required_artifacts=[audit-resolutions.md min_bytes:200], required_state_fields=[audit_findings_total present], required_sub_step_gates=[audit-resolution-walk-started, audit-resolution-walk-complete, audit-resolution-rerun-fired] |
| 2   | `scripts/lib/phase-manifest.schema.json`    | Add `audit-resolution` to phase-name enum                                                                                                                                                                                                                                                            |
| 3   | `scripts/sprint-advance-phase.sh`           | No code change — already manifest-driven (line 18-22 reads advances_to + predicates dynamically). New phase is data-only at this layer.                                                                                                                                                              |
| 4   | `scripts/lib/phase-predicates.sh`           | New predicate kind `audit_resolution_complete` (see Recommendation below)                                                                                                                                                                                                                            |
| 5   | `scripts/sprint-end.sh`                     | Update phase-list comments + ensure `verifying -> audit-resolution -> pre-deploy -> deploying -> done` sequence is enforced; reject end-from-verifying                                                                                                                                               |
| 6   | `scripts/sprint-replay-validator.mjs`       | Add `audit-resolution` to phase-name allowlist; backward-compat (G1) handled separately                                                                                                                                                                                                              |
| 7   | `docs/sprints/{USAGE,DEVELOPER,SCRIPTS}.md` | Operator-visible doc updates (W4)                                                                                                                                                                                                                                                                    |

The advancing machinery (`sprint-advance-phase.sh` lines 12-29) is already declarative — it reads the manifest at runtime and applies whichever predicates are listed. **Zero code change to the mutator.** This is exactly the payoff of T4 deterministic phases.

### Concern — exit-predicate complexity

The exit predicate is:

\`\`\`
resolved_count + len(deferred[]) + len(accepted[]) == audit_findings_total
AND every d in deferred[]: d.deferred_to_sprint != "" and d.ac_id != ""
AND every a in accepted[]: a.acceptance_rationale.length >= 30
\`\`\`

This is non-trivial arithmetic across three array sums plus per-element field checks. If we encode this as bespoke bash in `phase-predicates.sh` it becomes brittle (string math, jq escaping). If we encode it as a fresh predicate file kind that depends on spec.md, we create a coupling that breaks when spec.md amendments are in flight.

### Recommendation — pure-state jq predicate

Add a **new predicate kind** to `scripts/lib/phase-predicates.sh`:

\`\`\`
audit_resolution_complete:
jq_expr: (.audit_findings_resolved_count // 0) + ((.audit_findings_deferred // []) | length) + ((.audit_findings_accepted // []) | length)
== (.audit_findings_total // -1)
and ((.audit_findings_deferred // []) | all(.deferred_to_sprint != "" and .ac_id != ""))
and ((.audit_findings_accepted // []) | all(.acceptance_rationale | length >= 30))
\`\`\`

The predicate is **evaluable purely from `state.json`** — no spec.md dependency, no file-system race. The jq expression is testable in isolation against fixture state files. **This is ADR-2.**

## 3. AC-6 — `sprint-audit-resolve.sh` interactive walker

### Architectural choice

Interactive bash with `read -r` loop, ~350 LOC, walks each finding in `audit.json::.vulnerabilities[]`, prompts operator for **Fix / Defer / Accept**, captures rationale, persists.

### Concern — operator Ctrl-C mid-walk

Interactive bash + state persistence is a known fragile combo. If the operator is 6 findings into a 10-finding walk and hits Ctrl-C (or the SSH connection drops, or laptop sleeps), one of three things can happen:

1. **Best case:** the 6 already-recorded decisions are persisted; resume picks up at finding 7.
2. **Bad case:** the in-flight decision (finding 6, currently being typed) is lost — recoverable, but operator-confusing.
3. **Worst case:** mid-write to `state.audit_findings_deferred[]` was interrupted, state.json is corrupt.

Worst case is prevented by `atomic_update_state` (existing flock + tmpfile + rename pattern) — verified. Bad case is acceptable as long as the operator sees clearly: finding-6-not-recorded — please re-decide.

### Recommendation — atomic per-decision + resume-aware

Every Fix/Defer/Accept decision MUST be **one** atomic operation:

\`\`\`bash
atomic_update_state .audit_findings_deferred-plus-equals-d --argjson d "\$decision_json" \\
&& record_sub_step audit-resolution-finding-\$har_id-decided PASS
\`\`\`

These two writes happen in sequence (not atomically together — record_sub_step is a separate atomic write), but both being individually atomic means the worst-case observable inconsistency is decision-in-state-but-sub_step-missing — which `audit_resolution_complete` predicate handles gracefully (state is source of truth; sub_step is audit trail).

Resume logic on script start: read `(.audit_findings_resolved // []) + .audit_findings_deferred + .audit_findings_accepted | map(.har_id)`, then iterate `audit.json`.vulnerabilities[].har_id`and`continue` past any har_id already in that set.

The walker is **idempotent and resumable** by construction — no operator action needed beyond re-running the script. **This is ADR-3.**

## 4. AC-7 — `sprint-audit-rerun.sh` diff algorithm

### Architectural choice

After operator selects Fix and writes code, re-fire `ruflo daemon trigger audit`, diff `.vulnerabilities[]` against the baseline captured at audit-resolution phase entry, return 0 if the target finding is gone, 1 if it regressed.

### Concern — audit non-determinism causes false-positive regressions

Audit workers run an LLM under the hood. Even with temperature=0 and identical input, ruflo audit findings are not strictly deterministic — line numbers may shift by plus/minus 2, description text may rephrase, occasionally a finding disappears or reappears between back-to-back runs on identical code. We saw this empirically in the prior sprint.

If we treat **any** post-fix regression as blocking, operators will hit false positives, lose trust, and start `SPRINT_BYPASS_GATE`-ing the rerun — exactly the failure mode this sprint exists to eliminate.

### Recommendation — two-strikes regression rule

`sprint-audit-rerun.sh` re-runs the audit **twice** on any regression:

1. Run 1: target HAR-N gone, no new findings -> PASS.
2. Run 1: target HAR-N gone, but new finding X appears -> run audit again (Run 2).
3. Run 2: finding X still present -> BLOCK (real regression).
4. Run 2: finding X absent -> PASS (Run 1 was LLM jitter).

Cost: ~30s extra per false-positive, which is acceptable given audit-resolution phase has a 4-day budget. Record both runs to `state.audit_runs[]` so the dashboard can show jitter rate over time (signal: if jitter > 20%, escalate to ruflo for determinism tuning). **This is ADR-4.**

## 5. AC-10 / AC-12 — Encryption for `memory.json` + `session.json` (HAR-2 / HAR-4)

### Architectural choice

Wrap `loadMemory`/`saveMemory` (in `.claude/helpers/memory.js`) and the equivalents in `.claude/helpers/session.js` with **node built-in crypto** (`aes-256-gcm` + `scryptSync` key derivation). Zero new npm deps per the locked decision in section H. Key stored at `~/.claude-flow/.encryption-key`, mode 0600, generated via `crypto.randomBytes(32)` on first run.

This is correct:

- Node built-in `crypto` is FIPS-compatible at the AES-GCM primitive level, MIT-equivalent license, zero supply-chain surface.
- AES-GCM is AEAD — provides both confidentiality and integrity; the ciphertext is self-validating.
- Plaintext-detection on load (look for `{` as first non-whitespace byte) + transparent migrate-on-first-write means existing `memory.json` / `session.json` data does not break.

### Concern — key rotation / key loss

What happens when `~/.claude-flow/.encryption-key` is deleted (operator wipes `.claude-flow` to reset), corrupted (disk error), or rotated (security best practice)? Current spec is silent. Three failure modes:

1. **Key deleted, no backup:** all encrypted memory/session data is permanently unreadable. Operator sees opaque auth-tag-mismatch error.
2. **Key rotated:** old data encrypted with key v1; new key v2 cannot decrypt. Silent data loss on next load.
3. **Multi-machine drift:** if operator copies `.claude-flow/` between machines but not the key file, same opaque failure.

### Recommendation — versioned key + recovery doc

Encrypted payload format:

\`\`\`json
{
"format": "lifeos-enc-v1",
"keyVersion": 1,
"iv": "<base64>",
"authTag": "<base64>",
"ciphertext": "<base64>"
}
\`\`\`

On load:

- `format` does not equal `lifeos-enc-v1` -> treat as legacy plaintext, migrate.
- `keyVersion` does not match current key file version -> **fail loudly** with message:
  > `[memory] Cannot decrypt: payload key version 1, current key version 2. Recovery: see docs/sprints/_guides/encryption-key-recovery.md`
- Auth-tag mismatch -> same loud failure, point at recovery doc.

The recovery doc (new file in this sprint, scoped under AC-10/AC-12 deliverables) documents: (a) why this happens, (b) how to restore from key backup, (c) how to nuke + reset if no backup, (d) what data is lost in that case. Operator never sees an opaque crypto error without context. **This is ADR-5.**

## Conditions for Approval

The sprint is approved subject to all three conditions holding at sprint-end. If any fails, sprint cannot close as Production.

### Condition 1 — Predicate `audit_resolution_complete` is fixture-tested in isolation

Before AC-5 is marked Production:

- `scripts/lib/phase-predicates.test.sh` (or equivalent fixture test harness) MUST contain at least 4 test cases:
  1. All findings resolved -> predicate PASS
  2. Mix of resolved + deferred + accepted summing to total -> PASS
  3. One deferred entry missing `ac_id` -> FAIL with named field
  4. `audit_findings_total` unset -> FAIL with named field
- Fixture state files live under `docs/sprints/_fixtures/audit-resolution/`.
- The same predicate jq expression powers `sprint-advance-phase.sh` and the test — single source of truth.

### Condition 2 — Scope-bounding gate exercised against a real out-of-scope finding before W1 closes

AC-1/AC-2/AC-3/AC-4 cannot land as Production based on synthetic test alone. Required proof:

- Run `gate_audit_blocks` against this very sprint audit.json (which will contain the same HAR-1..10 noise the prior sprint surfaced, since W3 has not yet fixed them when W1 lands).
- Demonstrate in W1 proof file that gate returns **PASS** because all 10 findings map to files in W3 `## Files touched` claim — i.e., they are **in scope for this sprint** and intentionally not yet fixed.
- This is also the proof that AC-1 correctly distinguishes in-scope-not-yet-fixed from out-of-scope-advisory — the harder of the two semantic cases.

### Condition 3 — Encryption migration is reversible AND key-recovery doc exists before AC-10 ships

Before AC-10 lands:

- `docs/sprints/_guides/encryption-key-recovery.md` exists, >= 1KB, covers the 3 key-loss scenarios named in section 5 above.
- Memory/session helpers ship with a `--decrypt-to-plaintext` escape hatch (one-shot CLI flag, gated behind `LIFEOS_CONFIRM_DECRYPT=1` env var) so an operator can recover plaintext to a tmp file if a downstream tool is broken by encryption.
- The legacy-plaintext detection branch (`{` as first byte) MUST have at least one fixture test proving the migrate-on-first-write path is non-destructive.
